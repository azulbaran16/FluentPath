<objective>
Gate the phase on evidence. First prove against the live database that no learner's stored progress is damaged by the new contract, then run the full automated suite, then have a human confirm the four ROADMAP success criteria that no build step can prove.

Purpose: research flagged one assumption as high risk and explicitly refused to treat it as a finding — that every existing row in production `User.progress` parses cleanly under the new schema. If one does not, the safe-default read path would quietly zero a real learner's progress. This is a live database with an active beta user practising for a dated exam, so that assumption gets checked before anything ships, not after.

What makes "before anything ships" literal: Coolify deploys on a push to `main`, so this phase is executed on a dedicated branch and nothing is pushed until every gate below is green and the human checkpoint returns approved. Merging to `main` is therefore the deploy, and it is the step this plan stands in front of. That is also why the audit sits last rather than first — its whole value is running the *final* contract, schema module and merge included, against the rows production actually holds; an audit run earlier would prove a contract that later changed. Nothing in this plan modifies the Dockerfile or the deploy pipeline: D-09 stands.
Output: an audit report over live data, a green full suite, a corrected project instruction file, and a human sign-off or a concrete defect list.
</objective>

<task type="checkpoint:human-verify" gate="blocking">
  <name>Task 3: Human verification — the four Phase 2 success criteria</name>
  <what-built>Server-side progress. Postgres is now the authoritative copy for both the learning progress store and the CELPIP attempt store, each in its own column and its own endpoint. Both stores are single module-level instances behind useSyncExternalStore, reconciled once per authenticated load with a field-by-field merge that runs identically on client and server, so a write can be replayed or duplicated without regressing anything. The fields that can actually be deleted — vocabulary cards and CELPIP drafts — are selected on a millisecond activity instant stamped by every mutation and by nothing else, which is what keeps a deletion deleted when both devices were used on the same day, and what keeps a quiet page load from writing at all. Every write goes through a localStorage queue that survives a tab close, retries on full-jitter backoff, flushes on reconnect and at page-hide, and surfaces a discreet not-synced indicator only after failure has genuinely persisted. Payloads are validated with a shared zod contract that strips unknown fields and saves the rest, and corrupt stored data — in Postgres or localStorage — loads as the empty state.</what-built>
  <how-to-verify>
    Prerequisites: Docker Desktop running, `docker compose up -d db`, local DATABASE_URL pointing at the local Postgres, `npx prisma db push`, then `npm run dev`. Keep `npm run db:studio` open in a second terminal.

    1. Cross-device identity (criterion 1). Sign in, complete a scenario, add a vocabulary card and answer a grammar question wrong then right. Note the completions, XP, streak, CEFR level and due-review count on /dashboard. Open a **fresh browser profile or incognito window** — not just a new tab, localStorage must be empty — sign in as the same learner, and confirm all five figures match. Cross-check the row in Prisma Studio.
    2. Anonymous progress survives signup (criterion 2). In a fresh profile, signed out, complete two scenarios and confirm the local key holds them in DevTools. Sign in to an account that **already has different progress**. Confirm the account now holds the union: both the anonymous completions and the pre-existing ones. This is the half a server-wins implementation would silently pass, so check both directions.
    3. CELPIP history and the blank editor. Signed out, complete a CELPIP writing task. Sign in and confirm the attempt appears in the account's history and in the celpipProgress column. Then reopen that same task and confirm the editor is **blank** — a submitted answer must never pre-fill the next timed attempt.
    4. Same-day deletion survives a reconcile (D-01b). Do this whole step in one sitting, on one calendar day — that is the point of it, and it is the case a day-granularity rule cannot decide. Signed in on browser A, mark a vocabulary card as known and wait for the row to update in Studio. In browser B, a second profile signed in to the same account, load the app and confirm the card shows as known there too. Back in browser A, **un-mark that same card**, and reload A to confirm it stays un-marked. Now reload browser B and confirm the card is un-marked there as well. B's copy is both older and the larger set, so if the card comes back in either browser the whole-field selection is being decided by size rather than by the activity instant, and the un-mark will keep resurrecting for every learner. Then repeat the shape for drafts: in browser B type into a task's editor until a draft is saved, in browser A submit that same task, then reload B and confirm B's editor for that task is **blank** rather than restoring B's draft.
    5. Malformed write and corrupt stored data (criterion 3). With the dev server running and a valid session cookie, PUT a non-object body to /api/progress and confirm a 400; re-read the row in Studio and confirm it is untouched. Then PUT a body with one unknown extra field and a bad value for xp, and confirm it succeeds with the unknown field absent and the rest saved. Finally, in Studio, set that user's progress to a deliberately broken JSON string, load /dashboard, and confirm the empty state renders rather than a 500.
    6. Offline write reaches the server (criterion 4). Open DevTools, set the network to Offline, complete a scenario, and confirm the queue slot exists in localStorage. **Close the tab entirely.** Reopen it online, and confirm the write lands in Studio and the queue slot clears. Separately, keep the network offline long enough for three retries and confirm the discreet not-synced indicator appears, then restore the network and confirm it disappears on the next success.
    7. No noise on the happy path — both loops. With the network healthy, reload /review and confirm the Network tab shows **one** GET to /api/progress, not four. Then reload /dashboard several times with no learner activity at all and watch two things: the Network tab must show one GET to /api/progress and one to /api/celpip-progress per load and **no PUT to either**, and the User row's updatedAt in Studio must not advance across those reloads. Both loops write the same row, so a single advancing timestamp means one of them is stamping the activity instant on its own reconcile — the PUT tells you which. Repeat the same reload check on /celpip while signed in, since that is where the CELPIP store is actually mounted.
    8. Anonymous learners see no indicator. Signed out, open /celpip and confirm no sync indicator appears anywhere.
    9. Audit sign-off. Confirm the Task 1 audit reported every production row clean, and that you are satisfied the beta user's data is safe. Nothing has been pushed at this point: the phase is on its own branch and merging to `main` is what deploys, so this sign-off is the gate in front of that merge.
  </how-to-verify>
