<objective>
Prove the whole Phase 2 architecture on one end-to-end path: a single shared progress store on the client, one reconcile per authenticated load, and a server that *merges* the incoming snapshot into the stored blob rather than overwriting it — with the merge itself living in a pure module both sides import.

This is the tracer. It is production code, not a prototype: every layer this phase touches is wired for real, and the only thing deliberately left for later plans is refinement of individual merge rules (02-02), payload validation (02-03), the retry queue (02-04) and the CELPIP domain (02-05).

Purpose: `useProgress()` is today a plain hook with its own React state, called from 17 sites (up to four concurrently on `/review`). Building per-load reconcile, a retry queue and a sync indicator on top of that would multiply every one of them by four. Hoisting to one module store is therefore the first move, and doing it inside the tracer proves the store, the merge and the server round-trip together.
Output: `src/lib/progress-schema.ts`, `src/lib/progress-merge.ts`, a rewritten store half of `src/lib/progress.ts`, `src/components/ProgressSync.tsx`, a merge-on-write `PUT /api/progress`, and `scripts/verify-merge.mts`.
</objective>

  <behavior>
    - Idempotence: `mergeProgress(a, mergeProgress(a, b))` deep-equals `mergeProgress(a, b)` — the property D-02's per-load reconcile rests on. Without it, XP inflates on every page reload.
    - Commutativity: `mergeProgress(a, b)` deep-equals `mergeProgress(b, a)` — without it the client and the server converge to different values and every load produces a write.
    - Associativity: `mergeProgress(mergeProgress(a, b), c)` deep-equals `mergeProgress(a, mergeProgress(b, c))` — three-way convergence across two devices plus the server.
    - Totality: `mergeProgress(null, x)`, `mergeProgress(x, undefined)`, `mergeProgress("garbage", x)` and `mergeProgress({}, {})` all return a well-formed state and never throw.
    - Never-lose: merging an account that already holds data with a non-empty anonymous cache keeps every completion key from both sides (PROG-05 read literally).
    - No ping-pong: `progressEqual(merged, serverCopy)` returns true when the merge changed nothing, including when the two objects carry the same record keys in different insertion orders.
  </behavior>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser → `PUT /api/progress` | An authenticated but untrusted client submits a full progress snapshot |
| Postgres `User.progress` → route handler | Stored text of unknown integrity is parsed on every read |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-02-01 | Tampering | `PUT /api/progress` write path | high | mitigate | Merge-on-write makes the write a semilattice join, so a stale, duplicated or out-of-order snapshot can no longer regress the stored row |
| T-02-02 | Information Disclosure | `/api/progress` GET and PUT | high | mitigate | No identifier is accepted from the client; `session.user.id` remains the sole key on both the `findUnique` and the `updateMany`, preserving the existing IDOR-safe shape |
| T-02-03 | Denial of Service | Stored-blob parse in GET | medium | mitigate | The unguarded `JSON.parse` at route.ts:17 is wrapped so a corrupt blob yields the empty state instead of a permanent 500 for that account |
| T-02-04 | Spoofing | Stale session cookie pointing at a deleted user | low | mitigate | `updateMany` plus the `count === 0` 401 is preserved verbatim, not replaced by `update` |
| T-02-SC | Tampering | npm/pip/cargo installs | low | accept | No package installs in this phase — zod, react and prisma are already direct dependencies |
</threat_model>
