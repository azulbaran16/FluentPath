<objective>
Give the progress path one shared runtime contract: a zod schema that strips unknown fields and saves the rest (D-08), recovers a known field with a bad value instead of failing the whole payload, drops a single malformed record entry instead of the whole record, and returns a safe default when the *stored* data is unreadable (PROG-03).

Purpose: today `PUT /api/progress` accepts any object and `GET` calls `JSON.parse` with no guard, so one corrupt blob turns into a permanent 500 for that account. D-08 is deliberately lenient — strip and save, never reject — which creates a size gap the schema alone does not close, so this plan also bounds the payload.
Output: `src/lib/progress-schema.ts` as the single source of runtime truth, a validated route, a validated client cache read, and `scripts/verify-schema.mts`.
</objective>

  <behavior>
    - An object carrying every known field plus one the app has never heard of parses successfully, and the result contains only the known fields.
    - A payload whose `xp` is a string parses successfully with `xp` at its default and every other field preserved.
    - A record holding one well-formed entry and one malformed entry parses successfully, keeps the good entry and drops the bad one — no fabricated placeholder is invented for the bad key.
    - Keys named `__proto__`, `constructor` or `prototype` inside any record are dropped rather than assigned.
    - A payload that is not an object at all fails validation, so the caller can answer 400.
    - Reading a corrupt stored string through the read helper yields the empty state and never throws.
    - Negative or non-integer numerics fall back to their defaults; `lastActive` and `due` only survive when they look like a day string.
  </behavior>
  <action>
    Extend `src/lib/progress-schema.ts` with the runtime contract, keeping the module free of the client-boundary directive, of React, of next and next-auth, and of `@/`-aliased imports so both the route handler and a plain node script can load it. Its only runtime import is `zod`, already a direct dependency at version 4.4.3 — install nothing.

    Build `progressSchema` from the plain object constructor, whose default behaviour is exactly D-08: unknown keys are dropped and the known ones are kept. Do not reach for either of the two modifier constructors — one keeps unknown keys, the other rejects the whole payload, and that rejection is the option the user explicitly turned down. Guard every known field with a per-field fallback so a stale client sending a bad value loses only that value: bounded non-negative integers for `xp`, `streak`, `todayXp` and `goalXp` (keep 30 as the goal default), a day-shaped string or null for `lastActive` and `xpDay`, a nullable string for `level`.

    Add `sanitizedRecord(itemSchema)` — a transform that walks the raw value with `Object.entries`, validates each entry, and assigns the survivors into a freshly created object, skipping any key named `__proto__`, `constructor` or `prototype`. Building the result with explicit assignment into a fresh object rather than a spread of unvalidated input is what keeps the prototype-pollution vector closed. This is D-08's own principle applied one level down: strip what does not fit, save the rest. Deliberately do not use the alternative of attaching a fallback to the entry schema — that keeps the bad key alive with an invented value, and inventing SRS schedule data is worse than dropping it. Provide a sibling helper that types its output as a partial keyed record so `skillXp` matches its declared `Partial<Record<Skill, number>>` type without a cast, taking `Skill` through a type-only import from `./curriculum` so no runtime dependency is added.

    Export `safeReadProgress(raw)` for reading *stored* data — the DB blob and the localStorage cache. It parses the string inside a try/catch and runs the schema with a top-level fallback to `EMPTY`, so it never throws. That asymmetry is the rule this phase runs on: reads are lenient and always produce a value, writes validate and only refuse when the body is not an object at all.

    Add the compile-time drift guard: a conditional-type equality assertion between the schema's *output* type and the hand-written `ProgressState` interface, assigned to a `true`-typed const. It compiles clean while the two agree and fails the existing `npx tsc --noEmit` check the moment a field is added to one side and not the other. Compare against the output type, not the input type — the per-field fallbacks make the two differ.

    Create `scripts/verify-schema.mts` alongside it, in the same style as `scripts/verify-merge.mts`: a `.mts` node script run with `--experimental-strip-types`, importing the schema module with an explicit extension, asserting every behaviour above and printing a one-line pass summary.

    Harden `PUT /api/progress`. Keep the `auth()` preamble and its 401 shape byte-for-byte. Read the request body as text first and answer 413 when it exceeds one mebibyte, before parsing — D-08's leniency says nothing about size, and an authenticated client posting a huge blob is the one denial-of-service this design opens. Then parse the text inside a try/catch and validate the `progress` envelope with `safeParse`, answering 400 only when the value is not an object at all; a known field with a bad value or an unknown extra field must still succeed, because a browser holding a cached older build has to keep saving. Read the stored blob through `safeReadProgress` so a corrupt row degrades to the empty state instead of throwing, and when it does degrade log once through `console.error` with the module prefix the repo uses, including the account id and no more than the first 200 characters of the offending string — never the email. Do not add a column to preserve the corrupt value; the row survives until the next successful write, which is enough for recovery, and D-09 keeps schema changes minimal. Merge the validated payload into the safely-read stored state with `mergeProgress`, recompute the denormalized `level` from the merged result, and keep `updateMany` with its `count === 0` 401 and its existing comment.

    Apply the existing in-memory rate limiter to the write path, keyed on the account id, with a window generous enough that a normal learning session with two open tabs never trips it (on the order of sixty writes per minute) and a runaway retry loop does. On refusal answer 429 and set `Retry-After` from the limiter's `retryAfter`, because the retry queue built in 02-04 honours that header.

    Apply the same contract to `GET`: read through `safeReadProgress` and return the parsed state.

This is the first time zod reaches the client bundle, so record the chunk total from `du -sb .next/static/chunks` after `npm run build` in the summary; the figure measured during research on this repo was 1170768 bytes across 30 chunks.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| authenticated browser → `PUT /api/progress` | Untrusted JSON crosses into persistent storage |
| Postgres / localStorage → app | Stored text of unknown integrity is parsed on every load |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-02-10 | Tampering | Progress payload validation | high | mitigate | zod validates every known field with bounded numerics and day-shaped string formats; unknown keys are stripped rather than stored |
| T-02-11 | Denial of Service | Unbounded blob storage | high | mitigate | Request body is length-checked before parsing and refused with 413 above one mebibyte — the gap D-08's strip-and-save leniency leaves open |
| T-02-12 | Tampering | Prototype pollution through record keys | medium | mitigate | `sanitizedRecord` walks entries and assigns into a fresh object, skipping `__proto__`, `constructor` and `prototype`; no spread of unvalidated input |
| T-02-13 | Denial of Service | Retry storm against our own server | medium | mitigate | Per-account rate limit on the write path answering 429 with `Retry-After`, which the queue honours |
| T-02-14 | Information Disclosure | Corrupt-blob diagnostic logging | medium | mitigate | The logged excerpt is truncated to 200 characters and carries the account id only — never the email or any credential |
| T-02-15 | Denial of Service | Corrupt stored blob | medium | mitigate | Reads go through a non-throwing helper with a top-level fallback, so one bad row cannot become a permanent 500 |
| T-02-SC | Tampering | npm/pip/cargo installs | low | accept | No package installs — zod 4.4.3 is already a direct dependency |
</threat_model>
