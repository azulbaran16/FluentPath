<objective>
Make a failed progress write survive the failure. Replace the fire-and-forget `fetch(...).catch(() => {})` with a coalesced queue persisted to localStorage (D-07), retried with full-jitter backoff, flushed on reconnect and at page-hide, and surfaced to the learner only once failure has genuinely persisted (D-06).

Purpose: PROG-04 says no silent data loss. Network failures often coincide with the learner closing the browser, so an in-memory retry is not enough — the queue has to outlive the tab.
Output: `src/lib/sync-queue.ts`, the queue wired into the store's single persist funnel, every flush trigger owned by the one app-wide mount, a discreet `SyncIndicator`, and `scripts/verify-queue.mts`.
</objective>

  <behavior>
    - `backoffDelay(n, rand)` with an injected deterministic `rand` returns 0 at the low end and stays strictly below `min(60000, 1000 * 2 ** n)`; the ceiling saturates at 60000 from attempt 6 onward.
    - Enqueueing twice for the same domain leaves exactly one slot holding the newer body and a higher sequence number — a full snapshot supersedes the one before it, so keeping the older one is pure waste.
    - The two domains hold independent slots: enqueueing a CELPIP snapshot leaves the progress slot untouched, which is what keeps an XP tick from re-uploading every essay.
    - Clearing a slot with a stale sequence number leaves the slot intact; clearing with the current one empties it. This is the guard against a live write landing while a flush is in flight.
    - `classifyFailure` maps a network error, a 5xx and a 429 to retry; a 401 to stop; a 400 and a 413 to drop-with-a-log.
    - The status turns stale only after three consecutive failures *and* more than thirty seconds since the last success, and returns to healthy on the next success.
    - A storage write that throws leaves the queue in memory and marks the status degraded rather than pretending the write persisted.
  </behavior>
  <action>
    Create `src/lib/sync-queue.ts` in the shape of `src/lib/rate-limit.ts`: a leading block comment stating precisely what the queue guarantees, what it does not, and when it should be replaced, then the exports. Keep it free of React so a node script can exercise it, and reach storage only through small internal helpers so a test harness can install a memory-backed store.

    Persist under the versioned key `fluentpath:sync:v1` — pick the colon separator deliberately to match `fluentpath:progress:v2` and note in the comment that the CELPIP store's dot separator is the older inconsistency, not the pattern to copy. Hold one slot per domain, `progress` and `celpip`, each carrying the snapshot body, a monotonic sequence number, an attempt count and the timestamp of the next permitted attempt. Read the slot file defensively, returning an empty queue on any failure, and write it through a helper that returns a boolean exactly as `celpip-progress.ts:58-65` does — if the queue itself cannot be persisted the retry is in-memory only, and the status must say so rather than silently evaporating.

    Export `enqueue(domain, body)` which overwrites the domain's slot with the newer snapshot, takes the next sequence number from the maximum already stored so the counter is shared across tabs and survives reload, and resets the attempt count. Export `backoffDelay(attempt, rand = Math.random)` implementing full jitter — a uniform draw below a capped exponential ceiling with a 1000 ms base and a 60000 ms cap — with `rand` injectable so the bounds can be asserted without flaking. Export `classifyFailure` returning retry, stop or drop per the mapping above; cap the *delay*, never the attempt count, because discarding a payload after N tries is exactly the silent loss PROG-04 forbids, while a coalesced single-slot queue costs a bounded amount of storage to keep forever. Treat 401 as the session having ended: stop the loop and clear the queued state rather than spinning. Treat 400 and 413 as permanent for that body — log through `console.error` with the module prefix the repo uses and drop the slot, since under D-08 those should be near unreachable and a real occurrence is worth seeing.

    Export `flushQueue()` guarded by a module-level single-flight flag so a page-hidden flush and a backoff-timer flush in the same tab cannot both fire. For each slot whose next-attempt time has passed, capture its sequence number, send it, and on success clear the slot only if the stored sequence number still matches what was sent — otherwise a write enqueued while the request was in flight would be thrown away. On a retryable failure increment the attempt count and schedule the next attempt from `backoffDelay`, honouring a `Retry-After` header when the server sends one. Keep a two-row constant mapping each domain to its endpoint and request envelope: the progress slot goes to the existing route with the `{ progress }` envelope, and the CELPIP slot to `/api/celpip-progress` with a `{ celpipProgress }` envelope — that route arrives in 02-05 and nothing enqueues to the CELPIP slot before then. Expose a small subscribable status (`subscribeStatus` / `getStatus`) carrying whether anything is pending, the consecutive-failure count, the last success time and whether storage is working, shaped so a component can read it with `useSyncExternalStore`; derive the stale flag from three consecutive failures together with thirty seconds since the last success, so three full-jitter attempts averaging well under ten seconds never trip it on a brief blip.

    Create `scripts/verify-queue.mts` in the style of the other verification scripts. Install a memory-backed storage object on the global before dynamically importing the queue module, then assert every behaviour listed above, including the compare-and-clear race and the staleness threshold in both directions. <threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| localStorage queue → `PUT /api/progress` | A snapshot authored earlier, possibly in another tab, is replayed against the server |
| queue retry loop → our own server | Client-controlled request rate crosses into our infrastructure |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-02-16 | Denial of Service | Retry loop after an outage | high | mitigate | Full-jitter backoff with a 60 s cap spreads reconnecting clients instead of letting them retry in lockstep, and the route's per-account rate limit from 02-03 backstops it |
| T-02-17 | Repudiation | Silent loss of a queued write | high | mitigate | The delay is capped, never the attempt count; only a classified-permanent rejection discards a slot, and that path logs |
| T-02-18 | Tampering | Replay of a stale snapshot | high | mitigate | Server-side merge-on-write from 02-01 makes replay a no-op, and sequence compare-and-clear stops a flush from discarding a newer queued write |
| T-02-19 | Elevation of Privilege | Queue payload carrying an identity claim | high | mitigate | The wire format carries no account identifier; the server derives identity from the session alone, and a 401 mid-replay stops the loop and clears auth-bound state rather than spinning |
| T-02-20 | Information Disclosure | Queued snapshot readable in localStorage | low | accept | The queue holds only the learner's own progress on the learner's own device, which localStorage already holds as the offline cache; encrypting it would need a key with nowhere safe to live |
| T-02-SC | Tampering | npm/pip/cargo installs | low | accept | No package installs — the queue is built on web platform APIs already inside the framework's stated browser baseline |
</threat_model>
