<objective>
Make one scenario — `social/small-talk` — genuinely practicable end to end, and build the four
pieces of plumbing the other thirty-four scenarios and fifty-two pairs will ride on: stable
authored ids, a namespaced SRS key space, a coverage registry that derives what is written from
what the banks hold, and a committed harness that gates all of it.

This is the tracer. It is deliberately one scenario wide and the whole stack deep: authored
content → composed id → `recordAttempt` → `state.srs` → the merge → the review flow. Everything
after this plan is expansion along a path that has already been proven.

Purpose: RESEARCH names three pieces of plumbing that CONT-01 and CONT-02 cannot be satisfied
without, and all three are cheapest to get wrong now and most expensive to get wrong after ~550
items exist. D-05 is the sharpest: today `ReviewView`, `ReviewHub` and `Dashboard` resolve every
due id through the global grammar bank, so a scenario phrase would be stored correctly, merged
correctly, scheduled correctly — and be invisible. D-03 is the other: a derived coverage registry
means execution can stop after any later plan without the app claiming practice it does not have.

Output: `social/small-talk` with its own six phrases and eight vocabulary cards feeding the review
queue; a coverage registry reporting 9/35 scenarios with phrases, 1/35 with vocabulary, 0/52 pairs
written and all 52 pairs pending; an honest "not written yet" panel wherever a declared skill has no
exercise; and `scripts/verify-scenario-content.mts` standing behind all of it.

**What the learner gains if execution stops right after this plan:** one scenario that is fully
practicable and feeds spaced repetition, every scenario page telling the truth about what it does
and does not offer, and — deliberately — the twenty-six scenarios with no phrase set of their own
no longer being handed a generic per-world set dressed up as scenario practice. That last one is a
temporary reduction in what is shown and an increase in what is true; plans 02–04 close it. It is
also the one thing a mid-phase stop makes visibly worse, so Task 1 writes it into `STATE.md` rather
than leaving it recorded only here, where a reader mid-phase would not look.

## The one-way door is already answered

**D-06 is ratified: the SRS id is the composite `world/scenario#kind#slug`** — for example
`social/small-talk#phrase#hows-it-going`. The user selected it at plan review on 2026-07-31, after
the plan checker independently confirmed the premise the recommendation rested on: all 39 existing
global grammar ids are slash-free, so a collision between the new key space and the old one is
structurally impossible rather than merely unlikely, and `sanitizeEntries` (`progress-schema.ts:411`)
passes such keys through untouched. The rejected alternatives were opaque global slugs, which throw
away provenance and need a second lookup table kept in step with the banks, and content-hash ids,
which silently orphan a learner's box-4 item the moment a typo is fixed.

This is a one-way door on live learner data and it is now shut in a chosen direction: execute
option A, do not re-open it, and do not spell the format out anywhere except through the id function
Task 1 creates. The blocking checkpoint that used to stand here has been answered and removed — this
plan is autonomous.
</objective>
