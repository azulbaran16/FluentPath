## What shipped

### Task 1 — the registry (commit `2428b05`)

`CelpipSkill` (`writing` | `reading` | `listening` | `speaking`) is a **new union sitting
above** `CelpipTaskType`, which was not touched. `CelpipTaskType` still types the stored
writing attempt's `taskType`, whose literal pair is mirrored independently in
`progress-schema.ts` and `progress-merge.ts` — widening it is what would silently delete a
live attempt on the next reconcile, and plan 01 paid for that lesson already.

**`CELPIP_SECTIONS` is the exact shape plans 04, 05, 07 and 09 need** (this is the record
the plan's `<output>` asks for):

```ts
export type CelpipCardIcon = "email" | "survey" | "speaking" | "reading" | "listening";

export interface CelpipSectionItem {
  id: string;        // the card's href is `${routePrefix}/${id}`
  title: string;
  summary: string;   // one line under the title
  timing: string;    // "27 min" · "30s prep · 90s speaking"
  icon: CelpipCardIcon;
}

export interface CelpipSectionGroup { key: string; label: string; items: CelpipSectionItem[] }

export interface CelpipSectionCoverage {
  available: boolean;   // DERIVED — groups with items > 0
  summary: string;      // DERIVED from counts; "" when unavailable
  caveat?: string;      // the ONE hand-written field; dropped when unavailable
}

export interface CelpipSection {
  skill: CelpipSkill;
  label: string;
  blurb: string;
  routePrefix: string;  // `/celpip/${skill}`
  groups: CelpipSectionGroup[];
  coverage: CelpipSectionCoverage;
}

/** What a bank hands the registry. `undefined` = the bank module does not exist yet. */
export interface CelpipSectionSource { groups: CelpipSectionGroup[]; summary: string }
```

**How a later plan wires a bank — one line.** `src/lib/celpip.ts` holds:

```ts
const READING_SOURCE: CelpipSectionSource | undefined = undefined;
const LISTENING_SOURCE: CelpipSectionSource | undefined = undefined;
```

Plan 05 replaces the listening `undefined` with `listeningSource(LISTENING_SETS)` (a local
builder in the same shape as the existing `writingSource()` / `speakingSource()`), plan 09
the reading one. Nothing else in `celpip.ts` and **nothing at all on the landing** changes:
`section()` filters empty groups, so availability, the tab treatment, the card grid, the
coverage line and the JSON-LD `teaches` all follow by themselves.

A per-section `caveat` is the fifth argument to `section()`. Plan 03's Task 3 caveat (Task 3
uses a written scene rather than a picture) goes there — one string, and it renders under the
Speaking tab. It is deliberately dropped when a section is unavailable, so a caveat written
ahead of its bank cannot appear.

Coverage is assembled from counts, never typed: writing reports
`"17 prompts across the exam's two writing tasks"` from `CELPIP_TASKS.length`; speaking
reports `"1 prompt covering 1 of the 8 exam task shapes"` from the bank's distinct `shape`
values over `CELPIP_SPEAKING_SHAPES.length`. `CELPIP_SPEAKING_SHAPES` is new — the eight
shapes as data, so the denominator moves on its own. It is presentation-only and is mirrored
nowhere in the persistence layer, where `shape` remains a bounded string.

`CelpipTabs` renders one tab per registry entry; **`COMING_SOON` is deleted**. An unavailable
section renders the same disabled pill with an `aria-disabled` badge reading "Not yet
available". The active-pill class string, the inline `--sky` style and `aria-pressed` are
unchanged, and the file still has no `"use client"`. `CelpipGroupTabs` is the second level,
rendered only when a section has more than one group — today Writing alone, which is the
asymmetry D-01 asks the UI not to hide.

`TaskCard` takes `title`, `summary`, `timing`, `href` and `icon` instead of a
`CelpipWritingTask`. Every visual is byte-identical: the accent bar that scales in on hover,
the `ProgressRing` status, the `rise` entrance with `animationDelay: ${index * 70}ms`, the
`--sky` accent and the `color-mix` status pill.

### Task 2 — one attempt history across skills (commit `35288fc`)

**`HISTORY_SOURCES` — the shape plans 05 and 09 append to:**

```ts
const HISTORY_SOURCES: HistorySource[] = [
  historySource<CelpipAttempt>({
    skill: "writing",
    read: (state) => state.attempts,
    title: (itemId) => getTask(itemId)?.title,
    meta: (attempt) => `${formatDuration(attempt.durationSeconds)} used · ${attempt.wordCount} words`,
  }),
  historySource<CelpipSpeakingAttempt>({ /* speakingAttempts, getSpeakingPrompt, … */ }),
];
```

`historySource<T extends { date: string }>` is generic in the attempt shape and erased to a
plain `HistorySource` at the boundary, so each entry keeps full type-safety over its own
record while the four can live in one array. It resolves the route prefix from the registry
once, and returns rows carrying `{ key, skill, itemId, title, href, date, meta }`.

An entry declares four things and inherits everything else — the sort, the empty state, the
count label, the per-card status, the href construction and the unresolved-id fallback. The
comment above the array says so in those words, because plans 05 and 09 depend on it.

Metrics are per skill. Writing keeps duration and word count; Speaking shows duration,
recording length or "no recording", and how many self-checks were ticked. The date is
rendered centrally by every row, so a new entry does not repeat it. **The old rollup printed
`wordCount` on every row**, which means nothing for a spoken or read attempt.

**T-02.1-08 as built:** an href is constructed only from the registry's route prefix plus an
id that resolved against a bank. A row whose id resolves to nothing is still listed — the
learner's history is hers — but renders as plain text reading "No longer available" rather
than as a link into a fabricated path.

Per-item attempt counts derive from the same rows the list renders, so a card's
"3 attempts" and the history below it cannot disagree. The keys are
`skill \u0000 itemId \u0000 date`; the id/date pair is the merge's own natural key, and the
skill prefix is there only because two records now feed one list.

The `ready`-flag discipline is unchanged and now has an assertion behind it (see below).

### Landing — 15 mutations, 13 caught, 2 survived and then closed

Caught: the unresolved-id href guard removed (T-02.1-08 defeated) · the speaking source
reading the writing record · speaking titles resolved through the writing bank · every row
linked to the writing route · the React key dropping the date · a silent attempt reported as
recorded · the self-check count including unticked items · writing metrics dropping the word
count · the default tab pointed at a section that does not ship · the speaking entry simply
missing · the newest-first sort removed · every row rendered as a link · a saved draft no
longer showing as in progress.

**Survived, then closed (2):**

1. **The `ready` gate could be deleted without a single failure.** The pre-hydration
   assertion seeded an *empty* state, which reports "not-started" whether the gate exists or
   not — the assertion had never been able to fail. It now renders the same *populated* state
   twice, once with `ready: true` and once with `ready: false`, and requires every card to
   read "not-started" in the second. Deleting `if (!ready) return "not-started"` now fails.
   This is the hydration-mismatch guard the plan calls out by name.
2. **Attempt counts could be keyed without the skill.** No writing task id equals a speaking
   prompt id today, so dropping the skill from the count key changed nothing observable. Now
   a fixture keys a *speaking* record by a *writing* task id and requires that writing card
   to stay "not-started" with a count of 0 — one skill's attempts must never complete another
   skill's item. The mutation now fails.

## Deviations from Plan

### [Rule 3 — blocking issue] The card ripple moved into Task 1's commit

Task 1's `<verify>` requires `npx tsc --noEmit` to pass, and it cannot while `CelpipLanding`
still passes a `CelpipTaskType` to a `CelpipSkill`-typed `CelpipTabs`. `TaskCard`'s
parameterisation and the landing's card grid therefore landed in Task 1's commit; Task 2's
commit is the history rework alone. Both commits type-check, lint and build on their own —
the alternative was a commit that did not compile. The plan anticipates this ripple ("Expect
that ripple; it is known, not a surprise"); only which commit carries it moved.

### [Rule 2 — missing critical functionality] `scripts/verify-celpip-sections.mts`

The derivation is this plan's entire justification, and nothing in the build would have
noticed a later edit replacing it with a hard-coded claim: `tsc` is perfectly happy with
`available: true`. 43 assertions now gate it, in the same no-runner, no-dependency style as
`verify-headers.mts`, with an explicit `.ts` import extension so it loads under
`--experimental-strip-types`. It **reports** which sections ship rather than asserting it —
an assertion on the phase's moving part would fail for most of the phase and end up disabled
rather than fixed, which is how a gate becomes decoration.

The filename is deliberately distinct from plan 03's `verify-celpip-content.mts`, which plans
05 and 09 extend; the two do not collide.

### [Rule 1 — defect in my own first draft] Raw NUL bytes made the extension point a binary file

The first version of `CelpipLanding.tsx` used literal NUL characters as key separators —
which is the convention `progress-merge.ts` already uses, and why git reports that file as
binary too. On a component that plans 05 and 09 must edit and that a human should be able to
review, a binary diff is a real cost: the commit landed as `Bin 6806 -> 11670 bytes`, no
insertions, no deletions. Replaced with `\u0000` escapes — identical at runtime, still
aligned with the merge's natural key, and the diff is text again. The commit was amended
before anything was pushed.

### [Judgement call] Where a caveat renders

The plan says the landing must say a caveat plainly; it does not say where. Caveats render on
the landing under their own section's tabs rather than in the hero coverage line. With four
skills the hero line would otherwise accumulate four parenthetical caveats, and a caveat is
most useful next to the section it qualifies. Plan 03's Task 3 note will appear when the
learner opens Speaking. Both are on `/celpip`.

### [Judgement call] `Headphones` imported into `icons.tsx`

The app had no listening glyph, and reusing `Mic` (speaking) or `MessagesSquare`
(conversation) would have read as the wrong skill. `lucide-react` is already a dependency —
**zero packages installed**, 11 + 11 unchanged. `icons.tsx` is not in the plan's
`files_modified`; it was touched because the registry deliberately keeps React and lucide out
of `celpip.ts` so the verification scripts can still load it.

### [Observation, not a deviation] `/celpip` is server-rendered on demand

`npm run build` lists `ƒ /celpip`, as it did before this plan. Unchanged behaviour.

## CELPIP-10 stays open, deliberately

The plan's own success criterion says CELPIP-10 is **structurally** satisfied, and it is: the
sections come from a registry, availability is derived, and the landing cannot silently
overclaim. The requirement's text is wider — "`/celpip` exposes Reading, Listening and
Speaking as real sections" — and two of those three still have no content. Marking it
complete here would be precisely the kind of overclaim this plan exists to make impossible,
so `REQUIREMENTS.md` is untouched and CELPIP-10 remains **Pending**. It closes when plans 05
and 09 wire the Listening and Reading banks — at which point the landing will say so by
itself, with no further edit.
