# Phase 2.1: CELPIP Remaining Skills — Research

**Researched:** 2026-07-30
**Domain:** Exam-format content modelling · Web Speech API (`speechSynthesis`) · `MediaRecorder` · extending a CRDT-style merge contract
**Confidence:** MEDIUM-HIGH (code claims HIGH and file:line-cited; exam-format claims MEDIUM — see Assumptions Log)

## Summary

Three things dominate this phase, and only one of them is code.

**First, the merge.** `CelpipProgressState` can be extended safely, but there is exactly one shape that is safe and several that quietly re-open the Phase 1 `fca41b7` defect. The state carries a **single** `updatedAt` instant (`src/lib/progress-schema.ts:166`) and that instant is already load-bearing for one whole-field-selected map, `drafts` (`src/lib/progress-merge.ts:785-797`). Adding a second whole-field-selected map that *shares* that instant breaks it: a device that stamps while saving a listening note would then also win the drafts map, resurrecting a cleared writing draft. The Phase 2 principle — *a selection key must travel with the value it selects* — means every new deletable map needs its own instant, and the cheap way to avoid that entirely is to **add no deletable maps at all**: model all three new sections as append-only attempt arrays with a natural key, exactly like `attempts`, and keep in-progress state in React only. There is also a live landmine: `celpipAttemptEntry` hard-codes the writing task-type pair at `src/lib/progress-merge.ts:671`, so an attempt with a new `taskType` would pass zod and then be **silently deleted by the merge**. Separate top-level fields per skill avoid that trap completely and leave the writing shape byte-identical for the beta user's live rows.

**Second, playback and recording both have concrete browser landmines, and one of them is a hard blocker in this repo today.** `next.config.ts:12` sets `default-src 'self'` and declares no `media-src`, so `media-src` inherits `'self'` — which does **not** match `blob:`. An `<audio src={URL.createObjectURL(recordingBlob)}>` will be **blocked by CSP**, meaning the Speaking section cannot play back a recording until `media-src 'self' blob:` is added. On the playback side, the repo's existing pattern (`src/components/practice/ListeningRoom.tsx:71`) speaks the whole clip as **one** `SpeechSynthesisUtterance`. That works for a 4-line clip and fails for a CELPIP-length script: Chrome truncates long utterances at roughly 15 seconds. Chunking by **speaker turn** solves the Chrome bug, keeps every utterance well under the limit, and simultaneously enables per-speaker voices for the multi-speaker exam parts — one design choice paying three ways. On iOS Safari `speak()` must originate in a user gesture, so all chunks must be queued **synchronously inside the click handler**, not chained from `onend`.

**Third, and this is the real bottleneck: authoring.** The existing Writing bank is 8 tasks in 255 lines (`src/lib/celpip/tasks-email.ts`), roughly 2,400 words of original prose. One *complete* Reading set covering all four exam parts is ~2,500 words of original prose plus ~38 items with options and explanations; one complete Listening set is ~3,200. That is, **one full Reading set costs about as much to write as the entire shipped Writing bank.** With an exam under three weeks away and D-07 saying structure fidelity beats volume, the defensible target is one complete set per skill first (every part shape represented), a second set only as capacity allows, and Speaking — which is cheap — done in full.

**Primary recommendation:** Add three separate append-only attempt fields to `CelpipProgressState` (never widen the writing `attempts` map or its `taskType` enum), keep every draft-like state in React so no new instant is needed, chunk Listening playback by speaker turn queued synchronously from the click, keep audio recordings entirely out of the JSON column and out of localStorage, and add `media-src 'self' blob:` to the CSP. Author one complete Reading set and one complete Listening set before authoring any second set.

## The Real CELPIP Exam Format

> **IP note:** what follows describes the exam's *structure* only — part names, task shapes, item counts and timings, which are publicly documented facts about the test. **No third-party passage, question, script, option, or model answer is reproduced anywhere in this document**, and none may be reproduced in the app (D-06, CELPIP success criterion 6).
>
> **Confidence caveat:** `celpip.ca` returned **HTTP 403** to automated fetches on 2026-07-30, so the numbers below come from third-party prep sites that agree with each other but are not the awarding body. Treat every item count and timing as `[CITED]`, not `[VERIFIED]`, and see Assumptions Log A1. The beta user very likely has official prep material that can settle these in one minute — that check is worth making before authoring 38 items per set to a possibly-wrong count.

### Whole test

The CELPIP-General test is entirely computer-delivered in one sitting, roughly 3 hours, with four components: Listening, Reading, Writing, Speaking. `[CITED: celpip.ca/take-celpip/test-format via web search]`

### Reading — 4 parts, ~38 questions, 55–60 minutes

| Part | Name | Items | Shape and question type |
|------|------|-------|-------------------------|
| 1 | Reading Correspondence | 11 | An email plus a reply. Roughly half are multiple-choice comprehension on the first email; the rest are **drop-down blanks inside the reply**, where the correct choice must fit both the facts of the first email and the reply's tone. `[CITED: celpipguide.com/test-format; celtestpip.com Reading Part 1 guide]` |
| 2 | Reading to Apply a Diagram | 8 | A diagram/brochure/schedule with point-form text, plus a short message about it. Reported as 5 questions on the diagram + 3 drop-down blanks in the message. `[CITED: celtestpip.com Reading Part 2 study guide]` |
| 3 | Reading for Information | 9 | A longer informational passage, often in labelled sections. Tests detail *and* inference; this is the part that carries a **"not given in the text"** style option, which is what makes it hard. `[CITED: celtestpip.com; prepcelpip.com]` |
| 4 | Reading for Viewpoints | 10 | An article presenting several viewpoints on one topic, plus a reader-comment paragraph with **drop-down blanks**. Tests distinguishing whose opinion is whose. `[CITED: celpipguide.com/test-format]` |

**What must be recognisable:** the drop-down-blank question type is not optional decoration — it appears in three of the four parts and is the type learners most often meet for the first time on exam day. A Reading section built only from 4-option multiple choice would look nothing like the real thing.

### Listening — 6 scored parts (plus an unscored practice task), ~38 questions, 47–55 minutes

| Part | Name | Speakers | Audio length | Items | Notes |
|------|------|----------|--------------|-------|-------|
| — | Practice Task | — | very short | 0 (unscored) | A volume/pacing warm-up before scoring begins. `[CITED: gurully.com/blog/celpip-listening-format]` |
| 1 | Listening to Problem Solving | 2 (M/F) | ~3 segments of 1–1.5 min | 8 | Questions follow **each** segment, not the whole part. Practical detail: numbers, times, procedures. |
| 2 | Listening to a Daily Life Conversation | 2 | 1.5–2 min | 5 | Casual register, implied meaning. |
| 3 | Listening for Information | 1 | 2–2.5 min | 6 | Structured explanation, sequencing. |
| 4 | Listening to a News Item | 1 | ~1.5 min | 5 | Factual recall. |
| 5 | Listening to a Discussion | 3 | 1.5–2 min (video) | 8 | Tracking who said what. Sources disagree here — celpipguide and celtestpip say 8, gurully says ~2. **Flagged, see A1.** |
| 6 | Listening to Viewpoints | 1 | ~3 min | 6 | Fact vs opinion. |

**The single most important structural fact:** *audio plays once, and questions appear after the audio, not before.* `[CITED: gurully.com/blog/celpip-listening-format]` This is exactly what D-04 and D-05 encode, and it is the whole reason the section trains anything.

**Implication for content authoring:** at a normal ~150 wpm speaking rate, the target script lengths are roughly — Part 1: three 200–250-word segments; Part 2: 250–300 words; Part 3: 300–380 words; Part 4: ~225 words; Part 5: 250–300 words across three speakers; Part 6: ~450 words.

### Speaking — 8 tasks, 15–20 minutes

| Task | Shape |
|------|-------|
| 1 | Giving advice in a personal scenario |
| 2 | Talking about a personal experience |
| 3 | Describing a scene (from an image) |
| 4 | Making predictions about a future situation |
| 5 | Comparing two options and persuading |
| 6 | Dealing with a difficult situation |
| 7 | Expressing and defending an opinion |
| 8 | Describing an unusual situation |

`[CITED: celpipguide.com/test-format; multiple prep sites agree on all eight names]`

Timings: each task gives **30–90 seconds of preparation** then a **60 or 90 second response**; response is reported as 90s for Tasks 1 and 7 and 60s for the rest. `[CITED: web search across celpipace.ca, clbready.com, prepcelpip.com — no official source reachable; see A1]`

**Note on Task 3:** it is image-based. Under D-01 (Speaking to a usable minimum) and the three-week ceiling, a written scene description the learner reads and then describes is an acceptable stand-in; sourcing or generating original images is a separate cost. Whatever is chosen, the landing must be honest about it (CELPIP-10 / criterion 5).

### Writing — already shipped

Task 1 email, Task 2 survey, 53–60 minutes combined. Out of scope for this phase (`02.1-CONTEXT.md` domain boundary).

### Pattern 1: Speaker-turn script chunking (the load-bearing one)

**What:** model a Listening script as an ordered array of `{ speaker, text }` turns rather than one string, and speak one utterance per turn.

**Why it is not a style choice — it solves four problems at once:**

1. It keeps each utterance far under Chrome's ~15-second truncation point without any timer hack.
2. It gives multi-speaker parts (Part 1: two speakers; Part 5: three) genuinely distinct voices, which is what those parts actually test.
3. It makes the post-answer transcript (D-04) renderable with speaker labels for free — and the transcript is the *only* place the text may ever be shown.
4. It leaves an obvious slot for `audioUrl?: string` per part when VOICE-01 lands, satisfying D-03's reversibility note with no data migration.

**Shape:**

```ts
// src/lib/celpip/listening-sets.ts — ALL content original (D-06)
export type CelpipListeningPartKind =
  | "problem-solving" | "daily-conversation" | "information"
  | "news-item" | "discussion" | "viewpoints";

export interface ListeningTurn {
  /** Display name in the post-answer transcript, and the voice key. */
  speaker: string;
  text: string;
}

export interface ListeningSegment {
  id: string;
  turns: ListeningTurn[];
  /** Reserved for VOICE-01. Absent today; adding it later is additive. */
  audioUrl?: string;
}

export interface ListeningPart {
  kind: CelpipListeningPartKind;
  title: string;
  /** Part 1 is several segments each followed by its own questions;
   *  every other part is a single segment. Modelling all parts as an
   *  array of segments avoids a special case. */
  segments: ListeningSegment[];
  questions: CelpipQuestion[];   // keyed to a segment id
}
```

**Critical iOS constraint on how it is played:** every chunk must be handed to `speechSynthesis.speak()` **synchronously inside the click handler**. iOS Safari rejects `speak()` that is not part of a user gesture, and a call chained from a previous utterance's `onend` is no longer part of one. `speechSynthesis` is a queue, so queueing all turns up front is both legal and simpler.

```ts
// Source: pattern derived from the repo's existing usage
// (src/components/practice/ListeningRoom.tsx:68-81) plus the iOS gesture
// requirement [CITED: weboutloud.io/bulletin/speech_synthesis_in_safari]
function playOnce(turns: ListeningTurn[], voiceFor: (s: string) => SpeechSynthesisVoice | undefined) {
  const synth = window.speechSynthesis;
  if (!synth) return false;
  synth.cancel();                       // clear anything the app queued earlier
  let started = false;
  turns.forEach((turn, i) => {
    const u = new SpeechSynthesisUtterance(turn.text);
    u.lang = "en-US";
    u.rate = 0.95;                      // matches the app's existing pacing
    const v = voiceFor(turn.speaker);
    if (v) u.voice = v;                 // absent voice → browser default, not a crash
    if (i === 0) u.onstart = () => { started = true; };
    if (i === turns.length - 1) u.onend = () => onPlaybackComplete();
    u.onerror = () => onPlaybackFailed();
    synth.speak(u);                     // ALL queued inside the gesture
  });
  return true;
}
```

### Pattern 2: The audio check as the gesture anchor

**What:** an unscored "test your audio" step before the timer starts — which is also what the real exam does with its unscored practice task.

**Why:** it is not just fidelity. It is the failure valve for the entire Listening section. D-04 forbids showing the script and D-05 hides the questions until playback ends, so a learner whose audio silently fails has *nothing on screen and no way forward*. Anchoring the first `speak()` in a deliberate button press also satisfies the iOS gesture rule at the exact moment the learner is paying attention to whether sound came out.

**When to use:** once per Listening set, before the timer is armed. Offer a single explicit "I heard that / I heard nothing" branch; the "nothing" branch must lead somewhere real (retry, browser guidance, and — since this is practice, not an exam — an escape that reveals the transcript rather than stranding her).

### Pattern 3: Append-only attempt fields, one per skill

**What:** three new top-level fields on `CelpipProgressState`, each `Record<string, XAttempt[]>`, each merged with the *existing* `unionRecord` + `canonicalAttempts` rule. See the Persistence section below for the full argument.

**Why not one polymorphic `attempts` map:** because of `src/lib/progress-merge.ts:671`. See Don't Hand-Roll #1.

### Anti-Patterns to Avoid

- **One long utterance for a whole script.** `ListeningRoom.tsx:71` does `clip.lines.join(". ")`. Correct for a 4-line clip, silently broken for a 300-word CELPIP script under Chrome.
- **Chaining chunks from `onend`.** Works on desktop Chrome, fails on iOS Safari after the first chunk.
- **Using `speechSynthesis.pause()` as the exam pause.** On Android `pause()` is implemented as cancel, and `paused` is not reliably updated. `[CITED: github.com/mdn/browser-compat-data/issues/4500]` Pause the *timer* (which `Timer.tsx:121-129` already does in practice mode) and treat audio as un-pausable.
- **Trusting `onboundary` for progress UI.** Not fired on Android, unsupported for many voices. `[CITED: mdn/browser-compat-data#28419]`
- **Persisting a per-question answer map that gets cleared.** Any map with a real delete site needs its own D-01b instant. See Don't Hand-Roll #2.
- **Storing audio anywhere durable.** See Don't Hand-Roll #3.
- **Blocking submission on a quality signal.** The house rule (`02.1-CONTEXT.md` — word count is a flag, not a gate; `RubricChecklist.tsx:5-7` — a partial self-check is a valid persisted state). A learner must be able to submit a Reading set with blanks unanswered and a Speaking attempt with no recording at all.

| Merging new attempt kinds | A new merge rule, a new instant, or a widened `taskType` enum | Three new `Record<string, T[]>` fields using the **existing** `unionRecord(x, y, canonicalAttempts)` rule (`progress-merge.ts:806`) | The existing rule is already proven idempotent/commutative/associative by 4,313 assertions. A new field that reuses it inherits the proof; a new rule needs a new proof. |
| Timed countdown | A second timer | `src/components/celpip/Timer.tsx` | Anchor-timestamp, does not drift in a background tab, handles `prefers-reduced-motion`, already has the pause affordance. |
| Self-evaluation UI | A new checklist | `RubricChecklist.tsx` + a new dimension array in `rubric.ts` style | Zero new component; the partial-check semantics are already correct. |
| Offline/retry/sync | Anything | The existing `sync-queue.ts` `celpip` slot, reached via `persist()` | D-08 says do not invent a second storage path. |
| Recording container choice | Hard-coding `audio/webm;codecs=opus` | `MediaRecorder.isTypeSupported()` probed in preference order | Safari 14.1–18.3 supported **only** MP4 and returned `false` for WebM; 18.4 added WebM/Opus. `[CITED: webkit.org/blog/11353/mediarecorder-api; blog.addpipe.com]` |
| Voice selection | Assuming a named voice exists | `getVoices()` filtered by `lang.startsWith("en")`, with the `voiceschanged` listener, and a graceful fall-through to the browser default | Available voices vary wildly by OS/browser; `getVoices()` is frequently empty on first call. `[CITED: developer.mozilla.org/.../SpeechSynthesis/getVoices]` |

**Key insight — three specific traps, each with a citation:**

**#1 — The `taskType` enum is a silent-data-loss trap.** `celpipAttemptSchema.taskType` is `z.enum(["email","survey"])` (`progress-schema.ts:428`) and `celpipAttemptEntry` independently hard-codes `if (taskType !== "email" && taskType !== "survey") return null;` (`progress-merge.ts:671`). These are two separate literal lists that must move in lockstep. Widen only the schema and a `"reading"` attempt validates on the wire, is stored — and is then **deleted by the merge on the very next reconcile**, with no error anywhere. Worse, `CelpipAttempt.taskType` is typed from `CelpipTaskType` (`progress-schema.ts:130` → `celpip.ts:11`), which is also the discriminator on `CelpipWritingTask`, so widening it would let a *writing* task declare `taskType: "reading"`. And the drift guard at `progress-schema.ts:471` binds all of it: change one side and `npx tsc --noEmit` fails. **Separate fields sidestep every part of this**, and they leave the writing shape byte-for-byte identical — which matters, because the beta user's writing history is live data (`02.1-CONTEXT.md` specifics).

**#2 — There is only one `updatedAt`, and it is already spoken for.** `pickDraftsSide` (`progress-merge.ts:785-797`) selects the whole `drafts` map by comparing `x.updatedAt` to `y.updatedAt`. Add a *second* whole-field-selected map governed by that same instant and the two fight: a device that stamps while saving (say) a listening note now also wins the drafts map, and a draft cleared on the other device comes straight back — the `fca41b7` defect, resurrected. This is precisely the Phase 2 principle *a selection key must travel with the value it selects* (`progress-merge.ts:318-334`, and the executable counterexamples at `verify-merge.mts:933-1026`). Two ways out: give each deletable map its own instant field, or **have no new deletable maps**. Take the second. In-progress answers and listening notes stay in React state; the exam is one sitting and its scratch paper is not preserved either.

**#3 — Audio in the JSON column is not merely inelegant, it breaks three things.** (a) `writeLocal` puts the whole state into one localStorage key (`celpip-progress.ts:32,71-78`); localStorage is string-only with a ~5 MB origin quota, base64 inflates by ~33%, and a quota failure returns `false` — which would make the beta user's *Writing* drafts stop saving as a side effect. (b) `/api/celpip-progress` caps the body at 2 MiB (`route.ts:55`); a 90-second Opus recording is roughly 300–400 KB, ~500 KB base64, so about four saved attempts exceed it. (c) A 413 is classified `drop` by the retry queue (`sync-queue.ts:307`) — the slot is **discarded permanently**, so the learner silently loses her whole CELPIP sync, writing history included. The recording lives in a `useRef` object URL for the session, is `URL.revokeObjectURL`'d on unmount, and the attempt record stores only `{ recorded: boolean, durationSeconds, mimeType, sizeBytes }`.

## Extending `CelpipProgressState` — what a new field must satisfy

Read `src/lib/progress-merge.ts` and `scripts/verify-merge.mts` before touching either. Baseline on 2026-07-30, both green: `verify-merge` **4,313** assertions, `verify-schema` **158** assertions. `[VERIFIED: node --experimental-strip-types scripts/verify-merge.mts && … scripts/verify-schema.mts, run this session]`

### The five properties, and what each one concretely forbids

| Property | Proven at | What it forbids in a new field |
|----------|-----------|-------------------------------|
| **Total** | `verify-merge.mts:1318-1396` | Throwing on garbage. A new coercion function must drop unreadable entries, never throw, and never produce `undefined`-valued keys. |
| **Idempotent** | `verify-merge.mts:1138` | Any append, any counter bump, any array concat without de-duplication. D-02 reconciles on **every** authenticated load, so a non-idempotent rule grows the column on every page view. This is why `canonicalAttempts` de-duplicates on a natural key **and sorts** (`progress-merge.ts:715-729`) — an unsorted array is a different serialization of the same value, and the reconcile would write it back forever. |
| **Commutative** | `verify-merge.mts:1139` | Any rule that consults which side is "local" and which is "server". The identical function runs on both sides. |
| **Associative** | `verify-merge.mts:1140-1147` | Any per-entry rule that reads state-level data (the instant, another map) — a key union destroys the provenance such a rule needs. Also any rule whose tie-break reads a field the merge itself inflates (the rejected-rule-B counterexample, `verify-merge.mts:994-1011`). |
| **Additive / old blobs still parse** | `verify-schema.mts:465-490, 584-629` | Removing or narrowing any existing field. A field absent from a stored blob must recover to its own empty default, because the beta user's row was written before this phase. |

### Mechanical guards that will fail loudly if the change is incomplete

Adding a field to `CelpipProgressState` requires touching **six** places, and the repo's own guards catch five of the six omissions at build time:

1. `CelpipProgressState` interface — `progress-schema.ts:145-167`
2. `CELPIP_EMPTY` — `progress-schema.ts:169-173`
3. `celpipProgressSchema` — `progress-schema.ts:437-446` — *omit this and the server silently strips the field on every write* (the plain `z.object` constructor drops what it does not declare; this is exactly the hazard the comment at `:441-445` warns about)
4. `MERGE_CELPIP_EMPTY` — `progress-merge.ts:632-636` — a **deliberate second declaration**, kept honest only by `verify-merge.mts:1310-1316`
5. `celpipCoerce` — `progress-merge.ts:751-758`
6. `mergeCelpip` — `progress-merge.ts:799-813`

Guards: the `Identical<>` drift guard at `progress-schema.ts:471-474` fails `npx tsc --noEmit` on any mismatch between the interface and the schema's *output* type; `verify-merge.mts:1311` fails at runtime if the two empty literals diverge; the totality group asserts the merged result has **exactly** the contract's field set (`verify-merge.mts:1341-1345`).

### The recommended shape

```ts
// progress-schema.ts — additive; the writing fields are untouched.
export interface CelpipProgressState {
  attempts: Record<string, CelpipAttempt[]>;        // writing — UNCHANGED
  drafts: Record<string, string>;                   // writing — UNCHANGED
  readingAttempts: Record<string, CelpipReadingAttempt[]>;     // new
  listeningAttempts: Record<string, CelpipListeningAttempt[]>; // new
  speakingAttempts: Record<string, CelpipSpeakingAttempt[]>;   // new
  updatedAt: string | null;                         // UNCHANGED, still one
}
```

Each new attempt type must carry the same **natural key** the writing one does — `{ setId | promptId, date }` — because `attemptKey` (`progress-merge.ts:698-700`) joins exactly those two on a NUL and de-duplication depends on it. An entry lacking either is dropped rather than stored (`progress-merge.ts:671`, and `verify-merge.mts:1362-1381` proves why: an identity-less entry would be re-appended on every reconcile and grow the column forever).

The merge rule for all three is one line each, reusing what exists:

```ts
readingAttempts: unionRecord(x.readingAttempts, y.readingAttempts,
                             (p, q) => canonicalReading([...p, ...q])),
```

`canonicalAttempts` is currently typed to `CelpipAttempt` (`progress-merge.ts:715`) but reads only `.date` and the entry's `canonical()` form — so it generalises cleanly over `{ date: string }` rather than needing three copies. Whether to generalise or duplicate is a planner call; generalising keeps one proof.

**Bound the free-form text.** `CELPIP_MAX_TEXT` is 20,000 (`progress-schema.ts:396`) and exists because prose is the only unbounded thing in this payload. If a Speaking attempt stores a written self-note, or a Listening attempt stores the learner's typed notes, that string needs the same ceiling. Answer maps (question id → chosen option index) should be `sanitizedRecord(z.number().int().min(0).max(...))` so one malformed answer costs only itself — the established per-entry rule (`progress-schema.ts:262-267`).

**Re-check the 2 MiB body cap** (`route.ts:55`) once the new shapes are sized. Three answer maps of ~38 integers plus metadata is on the order of a kilobyte per attempt, so the headroom holds comfortably — but state it in the plan rather than assume it, because a 413 is a permanent drop (`sync-queue.ts:307`).

### What the verification must add

Extend `verify-merge.mts`'s `celpipStates` fixture array (`:1121-1132`) with states carrying the new fields. **This is the highest-leverage single action in the whole persistence change**: the idempotence/commutativity/associativity loop at `:1134-1148` is an O(n³) sweep over that array, so every fixture added is automatically exercised against every other under both bracketings. Add at minimum: a state with only new-skill attempts, a state with both writing and new-skill attempts, a legacy state with the new fields **absent entirely** (the beta user's row today), and a duplicate-attempt pair sharing a natural key.

## Common Pitfalls

### Pitfall 1: CSP blocks blob-URL audio playback — a hard blocker, today

**What goes wrong:** the Speaking section records fine, and then `<audio src={URL.createObjectURL(blob)}>` plays nothing. CELPIP-08's "so the learner can hear herself back" — the entire point of the feature — does not work in production.

**Why it happens:** `next.config.ts:12` sets `default-src 'self'` and the policy declares no `media-src`, so `media-src` falls back to `default-src`. `'self'` matches the origin's scheme/host/port; a `blob:` URL does not match it and must be listed explicitly. `[CITED: developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Content-Security-Policy/media-src]`

**How to avoid:** add `"media-src 'self' blob:"` to the `csp` array in `next.config.ts`. This is a **narrow** widening: it permits `<audio>`/`<video>` to load same-origin in-memory media and grants no script capability whatsoever (the dangerous directive for `blob:` is `script-src`). Note this also future-proofs VOICE-01 — a same-origin `audioUrl` needs no change, since `'self'` already covers it.

**Warning signs:** a console entry of the form *"Refused to load media from 'blob:…' because it violates the following Content Security Policy directive: default-src 'self'"*. It appears only in a real browser against the deployed headers — **`next dev` and unit-level checks will not surface it**, which is exactly why this belongs in the plan's verification steps and not in someone's head.

**Unverified detail:** whether Firefox's `<audio>` blob handling produces the same violation text. The directive semantics are specified and browser-independent; only the message wording is not verified.

### Pitfall 2: Chrome truncates long utterances at ~15 seconds, silently

**What goes wrong:** a 300-word Listening script starts playing, stops around 15 seconds in with no `onerror` and sometimes no `onend`. The learner has heard a third of the script and, under D-05, the questions never appear.

**Why it happens:** a long-standing Chromium defect (issues 41294170 / 679437, and 41346274 *"speechSynthesis fails for long text without warning and blocks the API"*). The limit is on speaking *time*, not word count. `[CITED: issues.chromium.org/issues/41294170, /41346274]`

**How to avoid:** chunk by speaker turn so no utterance approaches 15 seconds. Prefer this over the widely-circulated `resume()`-every-14-seconds hack, which is a timer fighting the engine and is itself known to misbehave on Android. Chunking is the same work as the multi-voice requirement, so it costs nothing extra.

**Warning signs:** playback that always dies at about the same elapsed time regardless of content.

**Unverified:** whether the defect is still present in the beta user's exact Chrome build. Since chunking is required for multi-speaker parts anyway, the recommendation does not depend on resolving this.

### Pitfall 3: iOS Safari — the phone case, and there are four distinct failures

The beta user may practise on a phone (`02.1-CONTEXT.md`), so these are not edge cases.

1. **`speak()` outside a user gesture is rejected.** A call from `useEffect`, `setTimeout`, or an `onend` chain goes silent. `[CITED: weboutloud.io/bulletin/speech_synthesis_in_safari]` → Queue every chunk synchronously inside the click.
2. **Backgrounding Safari mid-utterance can wedge the synthesizer** until the page is reloaded. `[CITED: same]` → Listen for `visibilitychange`, `cancel()` on hide, and treat the attempt as needing an explicit restart rather than pretending playback continued.
3. **The hardware silent switch mutes Safari audio** while Siri and other paths still work — the learner will report "it's broken" when the phone is on silent. → The audio-check step (Pattern 2) must say so in words.
4. **`getVoices()` may return an empty or unhelpful list.** One source reports Safari returning nothing at all. `[CITED: weboutloud.io — conflicts with other reports; treat as ASSUMED]` → Voice selection must be a *preference*, never a requirement: if no distinct voices are available, fall through to the default voice and distinguish speakers by an on-screen label plus a small `pitch` offset. Never block playback on a missing voice.

**Also:** `speechSynthesis` is a global singleton and the repo already knows it — `ListeningRoom.tsx:79` calls `cancel()` on stop. A new simulator that does not `cancel()` on unmount will keep talking over the next page.

### Pitfall 4: "Plays once" cannot be enforced, and pretending it can is worse than not trying

**What goes wrong:** the design treats non-repeatability as a guarantee. A page reload restarts the whole set; nothing in the browser prevents it.

**How to avoid:** enforce it *within the attempt lifecycle* — the play control disables once the first utterance starts, and if the learner replays anyway, record `replays: number` on the attempt so her own history is honest with her. That is worth more than a lock she can defeat in one keystroke. Pair it with a failure valve (Pattern 2) so "plays once" never becomes "plays never".

### Pitfall 5: `getVoices()` is empty on first call

**What goes wrong:** voice selection silently no-ops on first page load and works after a refresh — the classic "works on my machine, second time".

**Why:** the list is populated asynchronously in several browsers; `voiceschanged` is the signal. `[CITED: developer.mozilla.org/.../SpeechSynthesis/getVoices]`

**How to avoid:** read voices once at mount, subscribe to `voiceschanged`, and make every voice lookup return `undefined`-tolerantly (the `if (v) u.voice = v` in Pattern 1). Never await voices before allowing playback.

### Pitfall 6: `MediaRecorder` format assumptions

**What goes wrong:** `new MediaRecorder(stream, { mimeType: "audio/webm;codecs=opus" })` throws on Safari ≤18.3, which supported MP4 only. `[CITED: webkit.org/blog/11353/mediarecorder-api]`

**How to avoid:** probe with `MediaRecorder.isTypeSupported()` in preference order (`audio/webm;codecs=opus` → `audio/webm` → `audio/mp4` → `""` for the browser default) and store the resulting `mimeType` on the attempt. Handle the `getUserMedia` rejection paths explicitly — `NotAllowedError` (denied) and `NotFoundError` (no microphone) are different messages to the learner, and `PronunciationLab.tsx:86-92` already sets the precedent of distinguishing `not-allowed` from a generic failure.

### Pitfall 7: A submitted attempt pre-filling the next one

The Phase 1 lesson, named explicitly in `02.1-CONTEXT.md` specifics and fixed in `fca41b7`. `WritingSimulator.finalizeAttempt` (`WritingSimulator.tsx:97-111`) clears the draft in the same step as recording the attempt, and `finalizedRef` makes it idempotent across the several exit paths. Any draft-like state in the new sections must do the same — **or, per the recommendation here, not exist at all**, which removes the failure mode instead of re-defending against it.

### Pitfall 8: The landing must be honest, not merely updated

`CelpipTabs.tsx:8` lists `COMING_SOON = ["Speaking", "Reading", "Listening"]` and renders them disabled (`:42-53`). CELPIP-10 and success criterion 5 ask for *"honest about anything still missing"* — so removing a badge for a section that ships one set, or ships a text stand-in for Speaking Task 3's image, is not the same as being honest about it. Note also that `page.tsx` metadata, `<h1>`, and the JSON-LD `name`/`teaches`/`description` all still say **"CELPIP Writing Practice"** — three separate strings, plus the SEO description, that go stale the moment this phase ships.

## Content Volume That Actually Fits

### The measured baseline

`src/lib/celpip/tasks-email.ts` is **255 lines for 8 tasks** — about 32 lines each. Per task: a ~60-word scenario, 3 bullets, a ~180-word original model answer, 3 strategy tips ≈ **~300 words of original prose**. The whole shipped Writing bank (16 tasks across both files, 460 lines) is roughly **2,400–2,800 words of original prose**. `[VERIFIED: wc -l and file inspection, this session]`

### Estimated cost per new unit

| Unit | Original prose | Items | Rough total effort vs. one Writing task |
|------|---------------|-------|------------------------------------------|
| **Reading set** (all 4 parts) | ~1,300 w passages/emails/diagram data/comments | ~38 stems × 4 options + 38 explanations ≈ 1,200 w | **≈ 8× — about one whole Writing bank** |
| **Listening set** (all 6 parts) | ~1,700–2,200 w of speaker-turn script | ~38 stems × 4 options + 38 explanations ≈ 1,200 w | **≈ 10×** |
| **Speaking prompt** (one, any task shape) | ~60 w scenario + optional "what a strong answer does" note | 0 (no key, no scoring under D-02) | **≈ 0.3×** |
| **Speaking rubric** (one-off) | ~600 w, mirroring `rubric.ts` | — | ≈ 2× |

Two things make Reading and Listening expensive that are easy to under-count. **Explanations**: CELPIP-06 and CELPIP-07 both require *per-question explanations*, which roughly doubles the per-item cost over a bare answer key. **Distractors**: a plausible wrong option is harder to write than a correct one, and the drop-down-blank type needs options that are *grammatically* fine and only *contextually* wrong — that is the type's whole difficulty and it cannot be faked with obviously-wrong fillers.

### Recommendation

**Sequence, not a quantity.** Because D-07 puts structure fidelity above volume, the first set of each skill is worth several times the second: it is the one that teaches her what the format *is*. Author in this order and stop wherever the calendar stops:

1. **Speaking — all 8 task shapes, 1 prompt each** (~800 words + the rubric). Cheapest, unblocks a whole requirement, and it is the section she can rehearse repeatedly against a single prompt. Do it first precisely *because* it is cheap.
2. **Listening set 1 — all 6 parts.** Highest marginal value: it is the only skill where the format itself (hear once, questions after) is the thing being trained, and it is the format she cannot practise on paper.
3. **Reading set 1 — all 4 parts,** with at least one drop-down-blank group in Parts 1, 2 and 4.
4. **Speaking — a 2nd prompt per task shape** (~500 words). Still cheap.
5. **Reading set 2** and **Listening set 2**, in that order, only if time remains.

**Floor for the requirements to be honestly met:** one complete set per skill (items 1–3). **Realistic target under three weeks:** items 1–4 plus one of the two set-2s.

**Make the marginal set cheap.** Structure the content modules so adding a set is a pure append to an exported array in a new file — the way `EMAIL_TASKS` and `SURVEY_TASKS` compose into `CELPIP_TASKS` at `celpip.ts:68`. Then "author a second Reading set" is a content task with zero code risk, and can be dropped from the phase without touching anything else. **This is the single most important structural decision for surviving the deadline**, and it argues for shipping the code paths on a thin content bank rather than blocking any route on a full one.

**Two cost reducers worth taking:**
- Render Reading Part 2's diagram from **structured data** (a schedule, a fee table, a rules list) as JSX. Authorable inside the content module, greppable for the D-06 IP check, accessible, no asset pipeline.
- Reuse Listening scripts as Reading Part 3 passages? **No** — do not. The exam formats differ (a spoken talk and an information text read differently), and re-use would blunt exactly the format fidelity D-07 is buying. Named here only so it is rejected on the record rather than rediscovered under time pressure.

## Code Examples

### Feature-detecting and probing the recorder format

```ts
// Source: pattern per MDN isTypeSupported + WebKit's MediaRecorder announcement
// [CITED: developer.mozilla.org/.../MediaRecorder/isTypeSupported_static,
//         webkit.org/blog/11353/mediarecorder-api/]
const PREFERRED = [
  "audio/webm;codecs=opus",
  "audio/webm",
  "audio/mp4",          // Safari 14.1–18.3 supported ONLY this
] as const;

function pickMimeType(): string | undefined {
  if (typeof MediaRecorder === "undefined") return undefined;
  return PREFERRED.find((t) => MediaRecorder.isTypeSupported(t));
  // undefined → construct MediaRecorder with no options and let the
  // browser choose; read the actual type back off recorder.mimeType.
}
```

### Loading voices without racing the empty first call

```ts
// Source: MDN getVoices + voiceschanged
// [CITED: developer.mozilla.org/en-US/docs/Web/API/SpeechSynthesis/getVoices]
function useEnglishVoices(): SpeechSynthesisVoice[] {
  const [voices, setVoices] = useState<SpeechSynthesisVoice[]>([]);
  useEffect(() => {
    const synth = typeof window !== "undefined" ? window.speechSynthesis : undefined;
    if (!synth) return;
    const read = () =>
      setVoices(synth.getVoices().filter((v) => v.lang.toLowerCase().startsWith("en")));
    read();                                   // often empty on first call
    synth.addEventListener("voiceschanged", read);
    return () => {
      synth.removeEventListener("voiceschanged", read);
      synth.cancel();                         // never talk over the next page
    };
  }, []);
  return voices;
}
```

### Releasing a recording without leaking it

```ts
// Object URLs pin the blob in memory until revoked. The attempt record
// stores metadata only — the bytes never leave this component.
useEffect(() => {
  if (!url) return;
  return () => URL.revokeObjectURL(url);
}, [url]);
```

### Applicable ASVS Categories

| ASVS Category | Applies | Standard Control |
|---------------|---------|-----------------|
| V2 Authentication | no (unchanged) | `auth()` guard already on the route — `route.ts:124-127, 138-141` |
| V3 Session Management | no (unchanged) | next-auth, untouched |
| V4 Access Control | yes (inherited) | Every write is scoped to `session.user.id`; `updateMany` avoids a 500 on a stale cookie (`route.ts:204-210`). New fields inherit this — **no new route should be needed** |
| V5 Input Validation | **yes** | `zod` via `celpipProgressSchema`. New fields must use `sanitizedRecord`/`sanitizedArray` (which build results by explicit assignment into a fresh object and skip `__proto__`/`constructor`/`prototype` — `progress-schema.ts:230-250`), and every string must carry a max length |
| V6 Cryptography | no | Nothing cryptographic is introduced |
| V7 Error Handling / Logging | yes (caution) | `route.ts:113-118` logs the **full** unreadable blob at error level. Audio bytes in the column would do exactly that. One more reason for Don't Hand-Roll #3 |
| V12 Files / Resources | **yes (new)** | Microphone capture is new user-media handling. Recordings stay client-side and session-scoped; nothing is uploaded, so there is no new retention surface, no new deletion obligation, and no new subject-access surface |

### Known Threat Patterns for this stack

| Pattern | STRIDE | Standard Mitigation |
|---------|--------|---------------------|
| Prototype pollution via JSON record keys | Tampering | Already mitigated — `POISONED_KEYS` + fresh-object assembly (`progress-schema.ts:230-250`). New fields must go through `sanitizedRecord`, never a spread of unvalidated input |
| Unbounded blob growth → DoS / permanent sync loss | DoS | Per-string `CELPIP_MAX_TEXT`, per-body `MAX_BODY_BYTES` (`route.ts:55`), per-user rate limit (`route.ts:67`). **Re-verify the body cap against the new shapes** — a 413 is a permanent slot drop (`sync-queue.ts:307`) |
| CSP weakening while adding `media-src` | Tampering / XSS | Add **only** `media-src 'self' blob:`. Do not add `blob:` to `script-src` — that is the directive where `blob:` is genuinely dangerous. Keep `object-src 'none'` and `frame-ancestors 'none'` untouched |
| Microphone captured without clear intent | Info disclosure / privacy | Capture only inside an explicit press; stop all `MediaStreamTrack`s the moment recording ends (a live track leaves the OS recording indicator on and is alarming); never auto-start; never upload |
| Recording persisted where it can leak | Info disclosure | Session-scoped object URL, revoked on unmount. Not in localStorage, not in the JSON column, not in IndexedDB unless the planner explicitly decides otherwise and states the deletion path |
| Learner's own prose in error logs | Info disclosure | Existing, documented, accepted (`route.ts:96-106`). Do not widen it |

## Open Questions

1. **Should any Listening/Reading in-progress state survive a refresh?**
   - What we know: persisting it creates a map with a real delete site, which needs its own D-01b instant or it corrupts the drafts rule (Don't Hand-Roll #2).
   - What's unclear: whether the learner will actually lose work to an accidental refresh mid-set. Writing needed autosave because a 27-minute essay is a lot to lose; a Reading set is answer clicks, not prose.
   - Recommendation: **do not persist.** Match the exam (one sitting) and avoid the merge complexity entirely. Revisit only if UAT shows real loss.

2. **Speaking Task 3 is image-based. What ships?**
   - What we know: D-01 caps Speaking at "a usable minimum"; sourcing or generating original images is a distinct cost.
   - Recommendation: ship a written scene description as the stimulus, and say so plainly on the landing (CELPIP-10 asks for honesty about what is missing). Flag as a candidate for the user to decide during planning — it is a visible product compromise, not an implementation detail.

3. **Should recordings survive a page reload (IndexedDB) or only the session?**
   - What we know: `celpipProgress` and localStorage are both ruled out (Don't Hand-Roll #3). The repo uses no IndexedDB today.
   - Recommendation: **session-only for this phase.** The stated purpose is "play it back and self-evaluate", which happens seconds after recording. IndexedDB adds a new storage surface, a new deletion obligation, and a new failure mode for a benefit nobody asked for. Explicitly listed as Claude's discretion in `02.1-CONTEXT.md`.

4. **Is a "practice mode" offered, as in Writing?**
   - Listed as Claude's discretion. `Timer.tsx:121-129` already supports it for free. But note the interaction: pausing the timer cannot pause the audio (Anti-Patterns), so practice mode in Listening means "pause between playback and questions", not "pause during playback". Worth stating in the UI rather than letting it surprise her.

5. **Does the `/celpip` landing keep one shared attempt history or split per skill?**
   - Not decided by CONTEXT. The current history flattens `state.attempts` (`CelpipLanding.tsx:43-52`); with three more record fields it becomes four flatten-and-merge sources. A per-skill tab is probably clearer, but this is a planner/UI call, not a research finding.
