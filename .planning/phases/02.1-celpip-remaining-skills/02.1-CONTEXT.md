# Phase 2.1: CELPIP Remaining Skills - Context

**Gathered:** 2026-07-30
**Status:** Ready for planning

<domain>
## Phase Boundary

Reading, Listening and Speaking practice at `/celpip`, in the real exam's shape, before the
beta user sits it. Reading and Listening are built to depth; Speaking to a usable minimum.

Out of scope: automated scoring of any kind, recorded (human or premium-TTS) audio, and any
change to the Writing section that already ships.

</domain>

<decisions>
## Implementation Decisions

### Scope shape

- **D-01:** Uneven by design — **Reading and Listening to depth, Speaking to a usable
  minimum**. The user chose this over three thin sections or one deep one, on the reasoning
  that Reading and Listening are where format practice converts to score fastest.
  Speaking ships as timed prompts + browser recording + self-evaluation, nothing more.

- **D-02:** **No automated scoring anywhere.** Reading and Listening have objective answer
  keys, so they self-score against those. Speaking gets a descriptor checklist the learner
  fills in herself, exactly like Writing. No AI is involved in this phase — it must not
  block on Phase 5.

### Listening audio

- **D-03:** Audio comes from the **Web Speech API already used in the app**, not from
  recorded files. Accepted cost, stated by the user: it sounds more robotic than the real
  exam. Accepted benefit: it ships immediately, costs nothing, and still trains the two
  things that matter — note-taking under time pressure, and following speech you cannot
  re-read.
  — **Reversibility:** reversible — swapping in real audio later means adding a file per
  script, not reshaping the data model. Design the script type so an optional `audioUrl`
  can be added without migration.

- **D-04:** The learner must **hear, never read**, the script. The transcript may be
  revealed after answering, as review material — never before or during.

- **D-05:** Questions are **revealed only after playback**, matching the real exam, so the
  learner cannot read ahead and listen selectively.

### Content

- **D-06:** All content original. Third-party study material is a **format reference only**;
  no sentence may be copied. This is the same hard constraint as Phase 1 and is verified by
  grep plus review in the phase gate.

- **D-07:** Reading covers the exam's four parts (correspondence, diagram, information,
  viewpoints). Listening covers the exam's part shapes. Speaking uses the real task shapes.
  Structure fidelity matters more than volume — she needs to recognise the format.

### Persistence

- **D-08:** Attempts for all three sections persist through the **Phase 2 server-side
  contract** — the `celpipProgress` column, its zod schema, and `mergeCelpip`. Do not invent
  a second storage path. Extending `CelpipProgressState` is expected; it must stay
  idempotent, commutative and associative under the merge, and additive so existing stored
  blobs keep parsing.

### Claude's Discretion

- Exact number of passages/sets per skill, given the three-week ceiling
- Question-type mix within each Reading and Listening part
- Recording implementation (MediaRecorder), format, and whether recordings are kept locally
  only or synced — **note:** audio blobs are large; syncing them to the JSON column would
  be a mistake
- Timer durations per section, and whether practice mode is offered as in Writing
- How the landing communicates what is deep and what is minimal

</decisions>

<code_context>
## Existing Code Insights

### Reusable Assets
- `Timer.tsx` is skill-agnostic already: anchor-timestamp countdown that does not drift in a
  background tab, `prefers-reduced-motion` handling, vermilion warning at ≤120s, pause in
  practice mode. Reuse it for every timed section rather than writing a second timer.
- `RubricChecklist.tsx` + `rubric.ts` give the Speaking self-evaluation its shape for free.
- The Writing task/attempt types are the template for the new content types.
- `CelpipTabs.tsx` already renders Reading/Listening/Speaking as disabled with "Coming soon" —
  the wiring point for CELPIP-10.

### Established Patterns
- Content lives in typed modules under `src/lib/celpip/`, one file per bank.
- Attempts append to a per-task array; nothing is ever mutated in place.
- Stores hydrate from localStorage in a module store behind `useSyncExternalStore`, then
  reconcile with the server once per authenticated load.
- Never block submission on a quality signal (word count is a flag, not a gate) — the same
  restraint should apply to the new sections.

### Integration Points
- `CelpipProgressState` gains attempt shapes for the new skills — additive only.
- `/celpip` landing gains real sections and loses badges.
- New routes under `src/app/(catalog)/celpip/…` following the Writing route's shape.

</code_context>

<specifics>
## Specific Ideas

- The exam is **under three weeks away** (user, 2026-07-30). Scope decisions bend toward
  what the learner can practise this week, not toward completeness.
- The learner is a real person with a dated exam, not a test account. Her Writing attempt
  history is live data.
- Phase 1's lesson, learned the hard way: a submitted attempt must never pre-fill the next
  one. Any new draft-like state in these sections must clear on finalize.

</specifics>
