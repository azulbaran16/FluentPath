The hear-once, answer-after, explain-and-transcribe runner, wired to one complete authored

## What shipped

### Task 1 — the runner and its route (commit `ba34a8e`)

`ListeningPlayer.tsx`, a five-state machine: `brief → check → playing → answering → results`.

- **D-05 has exactly one signal.** `onCompleted` from `celpip-speech.ts` — attached to the
  last utterance and nowhere else — is the only thing that advances `playing → answering`.
  No timer, no `onboundary`, no word-count estimate.
- **Questions are revealed one at a time**, in audio order, with a position indicator, and an
  answered question is not revisitable. The selection lives in `pending` until she advances,
  so moving on is the deliberate act rather than a side effect of clicking an option.
- **Submission is never blocked.** `ReadingRoom` disables submit until every question is
  answered; this deliberately does not. A blank is a real exam outcome and scores as wrong.
- **`AudioCheck` arms the clock.** The timer does not run until the check resolves. `"heard"`
  and `"skipped"` start the set normally; `"no-audio"` sets `audioFailed` and runs it in read
  mode.
- **Expiry is the Writing two-way exit**, verbatim in behaviour: submit as-is, or continue
  untimed. Nothing is discarded.
- **`finalizeAttempt`** copies the Writing shape — `finalizedRef` early return, wired to both
  results exits (Retry and the back link's `onClick`), ref reset on retry. `notes` is not in
  the payload.
- **Backgrounding** cancels playback and requires an explicit restart, via a component-level
  `visibilitychange` listener on top of the driver's own.
- **Two things from `ClipPlayer` were not copied**: the pre-answer reveal control and
  unlimited replay.

The route mirrors the writing route exactly: non-async `generateStaticParams`, an awaited
`params` Promise, `notFound()` **called**, no `"use client"`, and a `LearningResource`
envelope whose `description` is assembled from part-kind labels rather than from the script.

## The defect this plan's own verification found

**The entire script and answer key were being served inline in the page's HTML.**

The route originally passed the resolved set to the client component. A prop crossing that
boundary is serialized into the RSC payload, and Next inlines that payload into the document.
Measuring the served HTML rather than trusting the rendered markup:

```
before:  secret strings checked: 42   leaked into the served HTML: 41
after:   secret strings checked: 42   leaked into the served HTML: 0
```

The rendered page showed only the brief. `view-source` showed the news item, all five stems,
all twenty options and all five explanations, as readable prose, before she had heard a word.
Invisible to `tsc`, to lint, to all seven verification scripts, and to anyone looking at the
page.

**Fix:** the route passes `setId`; the player resolves the set on the client. The words now
live in a JavaScript chunk instead — still reachable to anyone who opens the bundle, which is
exactly the posture T-02.1-25 already accepts for the answer key, but no longer one keystroke
away in the page she is looking at. Verified both ways: the payload now carries only
`["setId","listening-set-1"]`, and the bank is present in two `.next/static/chunks/*.js` files
(stated rather than implied — this is not secrecy, and claiming it would be worse than the
defect).

**Gated, not just commented.** A conjunction in the listening group asserts that the route
hands the player an id **and** never hands it a resolved set. Passing the id is not the
property being defended; not passing the set is. Reverting the route fails both halves.

## Deviations from Plan

### [Rule 1 — defect found by this plan's own verification] The script shipped in the page's HTML

Documented in full above. In scope by every measure: it is the plan's own `<done>` ("the
script text is unreachable in the DOM before submit"), its own threat T-02.1-22, and its own
two new files.

### [Rule 1 — defect in my own first draft] A raw NUL byte made `ListeningPlayer.tsx` binary to git

The first commit landed the component as `Bin 0 -> 32517 bytes`. One raw NUL had been written
into a React `key` template literal, so git classified the whole 795-line file as binary and
the diff was unreviewable. Exactly the hazard plan 04 recorded, arriving by a different route:
there it was the repo's deliberate NUL separator; here it was an accident inside a string
where no separator was wanted at all.

Replaced with `::` — the key only needs to be unique — by script rather than by editor, since
writing the escape by hand is what produces the byte. Commit amended, so `main` never carried
a binary source file. Every file this plan touched is now checked for NUL and control bytes as
a matter of course; all six are clean.

### [Rule 1 — defect in my own first draft] The replay counter could inflate under React's double-invoke

`setPlayedStage((played) => { if (played) setReplays(n => n + 1); return true; })` calls a
setter inside an updater, which React may invoke twice in development. `replays` is the one
number on the attempt whose entire job is to be believed — "plays once" is *recorded* rather
than enforced precisely because the recording is the honest part. Moved to a ref that the play
handler reads and writes in one pass.

### [Judgement call] One timer for the whole set, so `Timer`'s re-arm is not exercised

The plan says to use `Timer`'s reset-on-changed-`totalSeconds` behaviour to re-arm between
parts. `CelpipListeningSet` carries **one** `timeLimitMinutes` and no per-part duration, so a
per-part timer would have to invent durations, and keying `Timer` per stage would hand her the
full set time again on every part. The countdown is therefore armed once for the set.
`totalSeconds` never changes today, so that documented behaviour is available and unused. If a
later plan gives parts their own windows, it is the mechanism to reach for.

### [Judgement call] Replay is a practice-mode affordance only

The plan permits an optional replay control that counts into `replays`. It is offered **only
in practice mode**, on the answering screen, labelled "Hear it again (practice only)", with
the copy stating that the exam plays each part once and that every extra play is recorded. In
timed mode there is no replay control at all — the only way to start audio a second time is
after a reported failure or an interruption, and that counts too.

### [Judgement call] The audio-failure valve renders the script before answering

The plan requires that a playback failure "give her the transcript escape rather than a dead
screen", while T-02.1-22 requires that no transcript render path exist before submit. Both are
satisfiable only by reading the second as *no reveal control for a learner whose audio works*.
The words are reachable pre-answer from exactly two places, both failures: `AudioCheck`
returning `"no-audio"` (plan 04's shipped escape), and a `speakTurns` failure or interruption,
which offers "I can't hear anything — read the script". Both set `audioFailed: true`, which
reaches the attempt, the results metrics strip and the landing history row ("read, not
heard"). The grep gate passes on its own terms — no "show/reveal transcript" string exists —
and this is recorded here rather than left for a reviewer to discover, because passing a gate
on a technicality is worth less than saying what the code does.

### [Rule 2 — missing critical verification] A source-level assertion in a content harness

The listening group reads two source files to gate the server/client boundary. That is
off-theme for a harness about content banks, and it is there because the alternative was a
comment. The exception is labelled as one, in place, with the measurement that motivated it.

### [Judgement call] Additions to the harness group beyond the plan's list

Option-level assertions (at least two options, all non-empty, no duplicates), question-stem
non-emptiness, a sane `timeLimitMinutes`, `getListeningSet` resolution both ways, and two
landing assertions (every set is offered as an item; no card summary carries a line of the
script). Each is cheap and each caught a mutation.
