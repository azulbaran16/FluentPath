<objective>
Turn `/celpip` from a Writing-only landing into a skill-aware one that reports honestly on
what actually ships — and make that honesty structural rather than editorial, so it stays
true as the remaining content plans land or get dropped against the calendar.

Purpose: this is the plan that makes every later content plan a pure append. After it, a new
Reading or Listening set becomes discoverable, countable and describable on the landing with
no landing edit at all. It runs second, immediately after the tracer, precisely so that
whatever ships next is reachable.

Output: a `CelpipSkill` union, a section registry that owns labels, hrefs, icons and
coverage claims, a skill-aware history rollup, and a `/celpip` page that no longer calls
itself a Writing practice site in four different places.

**If execution stops right after this plan:** the learner reaches the shipped Speaking
prompt from the landing, sees Reading and Listening honestly marked as not yet available,
and her Writing history is unchanged.
</objective>

  <files>src/lib/celpip.ts, src/components/celpip/CelpipTabs.tsx</files>

  <reversibility rating="reversible">A registry is presentation data; replacing it later costs one file.</reversibility>
  <action>
    Introduce a `CelpipSkill` union in `src/lib/celpip.ts` — `writing`, `reading`,
    `listening`, `speaking` — and a `CELPIP_SECTIONS` array, one entry per skill, each
    carrying: the skill key, a display label, a one-line blurb, the route prefix used to
    build item hrefs, and a `coverage` function or value that reports what is actually
    present in the banks. Keep `CelpipTaskType` exactly as it is — it is the WRITING task
    union, it is bound to `progress-schema.ts` by a type-only reference and a drift guard,
    and widening it is forbidden for the reason recorded in plan 01. `CelpipSkill` is a new,
    separate union that sits above it.

    Make coverage derived, not written. A section is "ready" when its bank exports at least
    one item and "not yet" when it exports none, and the human-readable coverage line is
    assembled from counts the code can see — how many prompts, how many sets, which part
    kinds a set actually contains. Only the qualitative caveats are hand-written prose, and
    each of those is a single field on the registry entry so a later plan can correct one
    string. This is the mechanism that makes criterion 5 ("honest about anything still
    missing") survive the calendar: if a set is dropped from the phase, the landing tells the
    truth without anybody remembering to edit it.

    At this point the Reading and Listening banks do not exist yet. Give their registry
    entries a coverage source that reads an empty collection today and will read a real one
    once plans 04 and 07 create the bank modules. Do not create empty bank modules to satisfy
    the registry — have the registry entry hold `undefined` for a bank that has no module
    yet, and treat that as "not yet available". Later plans replace `undefined` with the real
    import, which is a one-line edit.

    Rewrite `CelpipTabs` to take `CelpipSkill` rather than `CelpipTaskType`, to render one
    tab per registry entry, and to derive the disabled-with-a-badge treatment from the
    registry rather than from the hard-coded `COMING_SOON` array — delete that array. Keep
    the existing active-pill class string and inline `--sky` style, keep `aria-pressed` on
    the interactive tabs, keep `aria-disabled` on the unavailable ones, and do NOT add a
    `"use client"` directive to this file: it is presentational and inherits the boundary
    from `CelpipLanding`.

    Writing has two task types under one skill, so the landing needs a second level for it.
    Keep that simple: when the active skill is writing, render both task-type groups (or a
    secondary control) rather than inventing a general two-level tab system. Uneven sections
    are the point of D-01, and the UI should not pretend the four skills are symmetric.
  </action>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| stored attempt records -> rendered history | Learner-controlled ids and titles reach the DOM and an href |
| public page metadata -> search engines | The JSON-LD and metadata make public claims about what the app teaches |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-02.1-08 | Tampering | history row href built from a stored item id | medium | mitigate | Build hrefs from the registry's route prefix plus an id that resolved against a bank; render a non-link row when the id resolves to nothing, rather than interpolating an unresolved id into a path |
| T-02.1-09 | Information disclosure | history rendering of stored fields | low | accept | The fields rendered are the learner's own metadata (dates, durations, counts). No raw-HTML injection API is used anywhere in these components; React escapes text by default |
| T-02.1-10 | Spoofing | public JSON-LD overclaiming coverage | medium | mitigate | Coverage is derived from bank contents; `teaches` and the description name only skills whose banks are non-empty |
| T-02.1-11 | Denial of service | history rollup over four attempt records | low | accept | Bounded by the 2 MiB column cap proved in plan 01; the rollup is memoised on the state records as the current one already is |
| T-02.1-SC | Tampering | npm/pip/cargo installs | high | mitigate | Zero packages installed in this plan; the icons and components all exist already |
</threat_model>
