<objective>
The tracer. One native scenario is carried the whole way — bank, derived coverage, spaced-repetition
ids, renderer, advertised session length, gate — so that the four scenarios after it are authoring
against a machine that has already been proved rather than one that is being invented under them.

`native/phrasal-verbs` is the tracer because it is the only scenario in the world that touches three
Class-A banks (phrases, vocabulary, grammar), and because research names it the best-specified of
the five: the pedagogical unit is verb + particle + sense, which is a criterion an author can apply
item by item rather than a matter of taste.

Depth creates the session-length problem in the same change that creates the depth, so this plan
solves it in the same change. It also lands the two gates research listed as Wave-0 gaps — the
payload ceiling and a deck-length claim — plus one this phase's own D-04 makes non-optional: a
committed way to detect an id being re-pointed onto different content.

**If execution stops right after this plan**, the learner has one genuinely deep native scenario
(18 phrases, 42 cards, batched, honestly timed), and every plan after it inherits a gate that makes
a silent re-point impossible. Nothing anywhere claims depth that is not written: coverage is
derived, so the other four scenarios simply continue to report their floors.

**Four tasks, deliberately, and each one narrow.** The id-stability gate and its fixture are the
single most load-bearing artifact this phase produces — every later plan's protection against a
re-point is that one script — so it gets a task of its own rather than riding along beside three
harness groups, and it lands second, immediately after the tracer, so the window it protects opens
before any risky work starts. One commit per task. If context runs short, stop after a **complete**
task and record which remain; the one thing this plan does not permit is a content commit landing
without the fixture regenerated beside it.

Purpose: prove the whole machine on one scenario before 100+ items exist.
Output: a deepened recall pair, a batched deck, and three new committed gates.
</objective>

This is the one thing `AGENTS.md` says has no detection today: an id whose content is re-pointed
silently transfers a learner's box and due date onto material she has never seen, with no migration
path and no way to find out afterwards. This phase deletes and replaces items on purpose (D-04), and
authors roughly 136 new ids besides, so it needs the detector before it does either.

Create `scripts/verify-id-stability.mts` plus its committed fixture
`scripts/fixtures/scheduled-item-ids.json`.

**Scope it to the scheduled kinds** — phrase, vocab and grammar — because those are the only ids a
Postgres `srs` entry is ever keyed by. Writing, reading and speaking compose ids for uniqueness and
storage scoping only; hashing them would gate prose nothing schedules.

**What is hashed is the WHOLE authored record, every field.** A phrase is `{en, es, tip, slug}` and a
card is `{term, es, example, slug}`; a grammar question carries its prompt, its options, its answer,
its explanation and its topic. Hash all of it — serialised with a stable key order so the digest does
not move when a field is reordered — because D-04's rule is *never edit the content behind an
existing id*, not "never edit its headline field". A hash over `en` alone would pass a rewritten
`tip`, and a hash over `term` alone would pass a rewritten `example`, which is precisely the edit an
author under fatigue is most likely to make. State the covered field list in the script header so the
scope is a written contract rather than an implementation detail a later reader has to infer from the
code.

**Four rules, and the third is what makes the gate complete rather than opt-in:**

- an id present in both the fixture and the tree must hash the same — re-pointing fails;
- an id in the fixture and not in the tree must appear in the fixture's own list of deliberately
  retired ids, each with a reason, so a deletion is auditable rather than merely survivable;
- an id in the tree and **not** in the fixture FAILS as an unrecorded addition. Adding items is free
  and always will be — what is not free is adding them without regenerating the fixture in the same
  commit, because an id that never enters the fixture is an id the re-point rule can never protect.
  The failure message says exactly that: run the update mode and commit the regenerated fixture
  beside the content;
- an id on the retired list must NOT be emitted by any bank — a retirement is final, and an id coming
  back is a re-point wearing a different hat.

That third rule is the difference between a gate that protects this phase's ~136 new ids and one that
protects only the handful that happened to exist when the fixture was first written. The fourth is
what later plans lean on: a plan that retires items proves the retirement held by running this gate,
rather than by grepping source, where a comment or a near-miss substring would make the check lie in
either direction.

**Update mode.** Give it a flag that regenerates the fixture, and say in the header that the
regenerated diff IS the review — spell out what a legitimate diff looks like, so a reviewer has a
shape to compare against rather than a judgement to make: **new id lines added, nothing removed
except into the retired list, and not one changed hash on an unchanged id.** A changed hash beside an
unchanged id is exactly the thing a reader should refuse.

Seed the fixture from the tree as Task 1 left it. Task 1 was pure additions and its own diff check
proves it, so the window this gate protects opens here — the plan that introduces it, and the point
after which every commit in the phase, starting with the very next task, has to regenerate it.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| authored bank → learner's stored `srs`/`attempts` | An authored slug becomes a key in Postgres via `scenarioItemId`; the merge unions those keys blindly and cannot delete one |
| client → `POST /api/progress` | The whole snapshot crosses as one body against a 1 MiB cap enforced on declared length and actual bytes; a 413 is a permanent drop, not a retry |
| bank contents → page claims | Every count on a scenario page is read off `items.length`; `minutes` is the one number still hand-written |
