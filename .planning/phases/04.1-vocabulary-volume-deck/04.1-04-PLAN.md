## Run the near-duplicate scan BEFORE regenerating the fixture

As written, Task 1's verify runs `verify-id-stability.mts --update` and Task 2 then scans for
near-duplicates and **rewrites cards**. That order is wrong and it contradicts this phase's own
rule: content is not final until the scan has run, so regenerating in Task 1 either bakes in a
hash you are about to invalidate or invites a second `--update` to launder it.

**"Twice is fine because it is uncommitted" is exactly the habit 04-07 came from.** Plan 03 hit
this, inverted the order, and regenerated once; do the same here.

**Correct order:** author the cards → run the near-duplicate scan and make every rewrite → *then*
`--update`, **once** → commit content and fixture together, atomically. Task 1's `--update` verify
becomes an idempotence check that runs after the scan, which is the only point at which it can
pass.
</ordering_correction>

  process in the same sitting tends to reproduce the same openings, and the ceiling was chosen to catch
  precisely that.
- Deliberately spend openings plan 03 did not: questions, imperatives, subordinate clauses, time and
  place adverbials, plural and mass-noun subjects, second person. A vocabulary example does not have to
  be a declarative sentence with a pronoun subject, and 260 of them should not be.

Run the harness at the batch's midpoint, not only at its end. A frame problem found at card 60 costs
sixty rewrites; found at card 120 it costs a hundred and twenty, and after the commit it costs
retirements.
